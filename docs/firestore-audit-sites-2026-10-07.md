# Auditoria local de sites — 07/10/2026

Escopo: `sites/controller.ts`, `platform/firestore/sites.ts`, consultas do executor de sites e uso de arquivos. Execução exclusivamente local com o `MemoryStore` existente; os resultados são simulação, não homologação do Firestore, Storage, DNS, OpenAI ou Easypanel. Nenhum site foi publicado em ambiente remoto.

O adaptador usa `FIRESTORE_ROOT=medsi/v1`. A seleção de projeto vem de `firebaseAdmin()` / `FIREBASE_PROJECT_ID`, e o bucket de `FIREBASE_STORAGE_BUCKET`; estes módulos não selecionam outro projeto. Isso não comprova por si só que o processo hospedado aponta para `medsi-80f4a`: a configuração efetiva e a homologação remota ficam na auditoria central.

Todos os 11 nomes de RPC de `siteOperations` já estão no dispatcher nativo. As quatro coleções de leitura de sites (`company_sites`, `company_site_domains`, `company_site_jobs`, `company_site_versions`) já têm registro `marketing.read`. A leitura de anexos por serviço já exige `company_id`. Não foi necessário acrescentar operação ou simular endpoint inexistente.

Regressões reproduzidas antes da correção: leitura pública retornava snapshot sem aprovação; roteamento de uma publicação aprovada falhava após edição privada; referência de anexo com `company_id` correto e `object_path` de outro tenant era aceita. Agora a publicação guarda `published_approval`, distinta da aprovação do rascunho. Registros anteriores só reutilizam aprovação existente se ela comprovar hash/revisão; não se cria aprovação para conteúdo antigo. Uma mudança de perfil continua impedindo novo roteamento/publicação; o conteúdo já publicado permanece como snapshot, conforme o comportamento existente. Arquivamento e revogação explícita impedem a leitura pública.

Pendências explícitas: não há rollback dedicado na API nem formulário de lead no site atual; o histórico permite leitura, mas essas funcionalidades de produto não foram inventadas nesta migração. A publicação chama o adaptador de hospedagem, porém não registra `routing_configured_at` para domínio próprio nesse caminho: após DNS verificado antes de publicar, `verify-domain` deve ser executado novamente para concluir o registro nativo de roteamento. Reconciliação/remoção de domínio no provedor, emissão real de HTTPS e chamadas de DNS/provedor não foram executadas nesta auditoria. Esses pontos impedem afirmar homologação completa de hospedagem.
